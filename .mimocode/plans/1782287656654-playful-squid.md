# План реконструкції Level Generator та Solver

## Статус: Готовий до реалізації

---

## Поточні проблеми (що обмежує масштабування)

### Солвер
1. **SortedList** — O(n) вставка замість O(log n). Головне вузьке місце
2. **Path copying** — `new List<Move>(path) { move }` на кожному кроці. O(depth) пам'яті на вузол
3. **`new int[256]`** в `GetHeuristic()` — алокація на кожен вузол. ~2M алокацій за 50K ітерацій
4. **Евристика надто вільна** — не враховує Blocked, арени, міжсмужні залежності
5. **50K ліміт** — для 10×7 недостатньо, solver повертає -1 навіть для розв'язних рівнів

### Генератор
1. **Рандомний scramble** — не контролює глибину розв'язку (scramble на 20 кроків → розв'язок на 8)
2. **Повне розв'язання для кожної спроби** — 50K ітерацій × 100+ спроб = 5M+ операцій
3. **Модель складності** — `PL × (1 + confusion + planningDepth)` не корелює з реальністю
4. **PruneLevel** видаляє смуги з оптимального шляху, але не з пасток

### Структура стану
- `byte[,]` — 2D managed array, погана локальність кешу
- `GetHashCode()` — O(R×S) кожен виклик
- `Equals()` — O(R×S) кожен виклик

---

## Рекомендована архітектура: Hybrid (Reverse Scramble + Optimized A*)

### Чому саме цей підхід

| Підхід | Переваги | Недоліки | Вердикт |
|--------|----------|----------|---------|
| A* Opt. | Прості зміни, зберігає оптимальність | Не розв'язує 10×7 | Частково |
| Bidirectional | Експоненційне прискорення | Асиметрія Blocked/FilterColors | ❌ |
| IDA* | Мінімальна пам'ять | Чутливий до евристики | Fallback |
| Beam | Швидкий | Не гарантує розв'язок | ❌ |
| Monte Carlo | Швидка оцінка | Не знаходить оптимальний шлях | Додатково |
| Reverse | Швидка генерація | Глибина ≥ target, але може бути коротше | Основа |
| **Hybrid** | Найкращий баланс | Складна реалізація | ✅ **Рекомендовано** |

### Архітектура

```
LayoutGenerator → ReverseScramble → HeuristicScorer → OptimizedSolver → DifficultyCalculatorV2
     (геометрія)     (динаміка)       (оцінка)          (валідація)        (складність)
```

## Фаза 1: Оптимізація солвера

**Файли:** `LevelSolver.cs`, `LevelState.cs`

### 1.1 Zobrist Hashing
- `ulong _zobristHash` в `LevelState`
- Таблиця: `ulong[ringCount, sectorCount, maxColors]` — випадкові 64-бітні числа
- Інкрементальне оновлення при Rotate/Slide: O(1) замість O(R×S)

### 1.2 BinaryHeap
- Замінити `SortedList<float, List<...>>` на `BinaryHeap<ExpandNode>`
- O(log n) insert, O(log n) extract-min

### 1.3 Parent Pointers
- `ExpandNode`: `{ int parentIndex; Move move; float g; float f; ulong zobrist; }`
- Реконструкція шляху: від цілі до початку по parentIndex
- Економія: ~70× менше пам'яті на вузол

### 1.4 Кешовані буфери
- `int[] _heuristicBuffer = new int[256]` — один на рівень
- `byte[,] _rotateBuffer` — для тимчасових обчислень

### 1.5 Сортування ходів
- Перед додаванням в open set: обчислити h для кожного кандидата
- Додавати спочатку ходи з найменшим h (раннє обрізання гілок)

### 1.6 Збільшення ліміту
- 50K → 200K ітерацій
- Timeout 30 секунд

### 1.7 Покращена евристика
```
h(state) = Σ_r [ (S - maxColorCount(r)) + arenaPenalty(r) + blockedPenalty(r) ]
```

**Очікуваний результат:** 5-10× прискорення, 80-95% знаходження розв'язку для 10×7

## Фаза 2: Reverse Scramble

**Новий файл:** `ReverseScrambler.cs`

### Алгоритм
```
1. Створити розв'язаний стан (кожна смуга = один колір)
2. Для кожного кроку scramble:
   a. Отримати всі легальні ходи
   b. Для кожного ходу оцінити:
      - Conflict score: +3 за кожен новий конфлікт
      - Undo penalty: -5 за зворотній хід (зберігати останні 3)
      - Diversity bonus: +1 за використання нової арени/смуги
      - Random noise: ±0.5
   c. Обрати хід з найвищим weighted score
   d. Застосувати хід
3. Результат: стан з глибиною ≥ targetDepth
```

### Ключові правила
- **Anti-undo:** Заборонити хід, що скасовує попередній
- **Conflict tracking:** Рахувати "неправильних" сусідів
- **Arena coverage:** Забезпечити використання хоча б 70% арен
- **Color balance:** Не дозволяти одному кольору домінувати в конфліктних позиціях

**Очікуваний результат:** Генерація < 0.1 сек, гарантована глибина ≥ targetDepth

## Фаза 3: Нова модель складності

**Новий файл:** `LevelAnalyzer.cs`

### 6 факторів

| Фактор | Вага | Обчислення |
|--------|------|------------|
| **Stripe Complexity** | 0.20 | `Σ (|uniqueColors(r)| - 1) / rings` |
| **Color Dispersion** | 0.15 | `mean(variance(positions(c))) for all colors` |
| **Dependency Score** | 0.25 `Σ (|uniqueColors(a)| - 1) / |arenas|` |
| **Arena Interaction** | 0.20 | `Σ overlap(a1, a2) for all arena pairs` |
| **Misleading Moves** | 0.10 | `1 - productiveMoves/totalMoves at each step` |
| **Candidate Diversity** | 0.10 | `viableMoves at each step (h(next) ≤ h(current)+1)` |

### Формула
```
Difficulty = pathLength × (1 + 0.20×SC + 0.15×CD + 0.25×DS + 0.20×AI + 0.10×MM + 0.10×(1-CD))
```

**Очікуваний результат:** Кореляція з суб'єктивною складністю > 0.8

## Фаза 4: Інтеграція в LevelGenerator

**Файли:** `LevelGenerator.cs`, `LevelGeneratorWindow.cs`

### Оновлений pipeline
```
1. LayoutGenerator.Generate(params) → LayoutTemplate
2. for attempt in 1..maxCandidates:
   a. solved = createSolvedState(template)
   b. scrambled = ReverseScrambler.Scramble(solved, targetDepth)
   c. score = LevelAnalyzer.Analyze(scrambled)
   d. if score < minScore: skip
   e. result = OptimizedSolver.Solve(scrambled)
   f. if result.found && result.pathLength ≤ maxLen:
      difficulty = DifficultyCalculatorV2.Calculate(...)
      if difficulty ≥ target: return level
3. return bestCandidate
```

### Оновлені GenerationParams
- `TargetSolutionLength` (15-20)
- `MinDifficulty`, `MaxDifficulty`
- `MinCandidateScore`, `MaxCandidatesPerLevel`

## Верифікація

1. **Генерація тестових рівнів:** 50 рівнів різних розмірів (5×5, 7×7, 10×7)
2. **Перевірка розв'язності:** кожен згенерований рівень має бути розв'язним
3. **Вимірювання часу:** кожен етап pipeline окремо
4. **Порівняння:** новий vs старий генератор на одних параметрах
5. **Ручна перевірка:** 10 рівнів зіграти вручну, оцінити складність
