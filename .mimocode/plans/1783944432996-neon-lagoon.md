# Notification Module — Архітектурний план

## 1. Огляд архітектури проекту

Color Rings — Unity 6 puzzle game з feature-based модульною архітектурою (54 модулі). Кожен модуль знаходиться під `Assets/Feature/<ModuleName>/` та містить:
- Сервісний інтерфейс `I*Service` + реалізацію (plain C#, не MonoBehaviour)
- Zenject інSTALLЕР (`Installer<Self>` базовий клас)
- ScriptableObject конфіги з ConfigProvider патерном (async завантаження через Addressables)
- SaveData — JSON через Newtonsoft.Json, зберігається в `persistentDataPath`

Ключові конвенції:
- Приватні поля з `_prefix`
- `BindInterfacesAndSelfTo<T>().AsSingle()` для реєстрації сервісів
- Конструкторний інжекцінг (без `[Inject]`)
- Платформо-специфічний код абстрагується за інтерфейсами (без `#if UNITY_ANDROID` в Feature модулях)

## 2. Залежність: Unity Mobile Notifications

Потрібно додати пакет `com.unity.mobile.notifications` до `Packages/manifest.json`.

### 3.7 NotificationConfigProvider.cs

```csharp
public class NotificationConfigProvider : INotificationConfigProvider {
    private readonly UniTask<NotificationConfig> _configTask;
    private NotificationConfig _config;

    public NotificationConfigProvider(UniTask<NotificationConfig> configTask) {
        _configTask = configTask;
    }

    public async UniTask Initialize() {
        _config = await _configTask;
    }

    public NotificationEntry GetEntry(NotificationType type) {
        if (_config == null) return null;
        foreach (var entry in _config.Entries) {
            if (entry.Type == type) return entry;
        }
        return null;
    }
}
```

### 3.9 NotificationService.cs (основна логіка)

Залежності (constructor injection):
- `INotificationConfigProvider` — для отримання конфігурації (Addressables)
- `INotificationScheduler` — для platform-specific операцій
- `IChallengeService` — для перевірки `IsDailyChallengeAvailable()`
- `ISaveDataModel` — для читання/запису стану
- `ISaveDataService` — для персистентності

**Ключові методи:**

**`Initialize()`** — викликається з `BootstrapState` після `LoadAll()`:
1. Перевірити чи є запланована нотифікація
2. Якщо є і час push вже минув — запланувати нову на завтра
3. Якщо є і час НЕ минув — нічого не робити (залишити існуючу)
4. Якщо Daily Challenge не розблокований — нічого не робити

**`OnDailyChallengeUnlocked()`** — викликається при досягненні level 12:
1. Перевірити чи вже є запланована нотифікація
2. Якщо є — нічого не робити
3. Якщо немає — запланувати першу нотифікацію на 24h з delivery window

**`OnDailyChallengeOpened()`** — викликається з `DailyChallengeStartPresenter.OnPlayButtonClick()`:
1. Скасувати існуючу нотифікацію (якщо є)
2. Розрахувати час доставки: `DateTime.Now.AddHours(24)`
3. Застосувати delivery window (10:00-20:00)
4. Запланувати нову нотифікацію
5. Зберегти стан в SaveData

**Приватні методи:**

**`ScheduleDailyChallengeForTomorrow()`** — планує push на завтра:
1. Отримати `NotificationEntry` для `NotificationType.DailyChallenge`
2. Розрахувати baseTime = DateTime.Now + 24h
3. Застосувати delivery window
4. Scheduler.Schedule(id, title, body, validTime)
5. Зберегти timestamp

**`CancelDailyChallengeNotification()`** — скасування:
1. Отримати notification ID з конфігу
2. Scheduler.Cancel(id)
3. Очистити timestamp

## 4. Алгоритм delivery window

```csharp
private DateTime ApplyDeliveryWindow(DateTime baseTime, int startHour, int endHour) {
    // Якщо час вже в межах вікна — повернути як є
    if (baseTime.Hour >= startHour && baseTime.Hour < endHour) {
        return baseTime;
    }
    
    // Якщо час до початку вікна того ж дня — перемістити на початок вікна
    if (baseTime.Hour < startHour) {
        return baseTime.Date.AddHours(startHour);
    }
    
    // Якщо час після кінця вікна — перемістити на початок вікна наступного дня
    return baseTime.Date.AddDays(1).AddHours(startHour);
}
```

Приклади:
- 09:20 → 10:00 (того ж дня)
- 22:15 → 10:00 (наступного дня)
- 18:30 → 18:30 (без змін)

## 5. Потік планування (Scheduling Flow)

### Перша нотифікація (коли гравець досягає level 12):

```
Гравець досягає level 12 (відкривається Daily Challenge)
        │
        ▼
LevelResultService або ChallengeService → _notificationService.OnDailyChallengeUnlocked()
        │
        ▼
Перевірити: чи вже є запланована нотифікація?
        │
        ├── Так → Нічого не робити
        │
        └── Ні → Запланувати першу нотифікацію
                │
                ▼
        Розрахувати baseTime = DateTime.Now + 24h
                │
                ▼
        ApplyDeliveryWindow(baseTime, 10, 20)
                │
                ▼
        Scheduler.Schedule(id, title, body, validTime)
                │
                ▼
        Зберегти ScheduledTimestamp в NotificationSaveData
```

### Повторне планування (коли гравець грає DC):

```
Гравець натискає Play в Daily Challenge
        │
        ▼
DailyChallengeStartPresenter.OnPlayButtonClick()
        │
        ▼
_notificationService.OnDailyChallengeOpened()
        │
        ▼
Скасувати попередню нотифікацію
        │
        ▼
Розрахувати baseTime = DateTime.Now + 24h
        │
        ▼
ApplyDeliveryWindow(baseTime, 10, 20)
        │
        ▼
Scheduler.Schedule(id, title, body, validTime)
        │
        ▼
Зберегти ScheduledTimestamp в NotificationSaveData
```

## 6. Потік перепланування (Rescheduling Flow — при старті гри)

### Сценарій А: Гравець заходить в гру ДО push (push на 15:00, гравець зайшов в 14:00):

```
OnGameStarted()
        │
        ▼
Чи є запланована нотифікація?
        │
        ├── Ні → Нічого не робити
        │
        └── Так → Чи час push ще не минув?
                │
                ├── Час MINUV (push мав бути о 15:00, зараз 16:00)
                │   → Запланувати нову на завтра (ScheduleDailyChallengeForTomorrow)
                │
                └── Час НЕ минув (push на 15:00, зараз 14:00)
                    → Залишити існуючу нотифікацію
                    → Гравець ПОВИНЕН зіграти DC, щоб перепланувати
                    → Якщо зіграв → OnDailyChallengeOpened() скасує + запланує нову
                    → Якщо НЕ зіграв → push лишається на сьогодні
```

### Сценарій Б: Гравець заходить в гру ПІСЛЯ push (push на 15:00, гравець зайшов в 16:00):

```
OnGameStarted()
        │
        ▼
Чи є запланована нотифікація?
        │
        ├── Ні → Нічого не робити
        │
        └── Так → Чи час push вже минув?
                │
                ├── Час MINUV → Запланувати нову на завтра
                │   (Гравець отримав push, тепер треба запланувати наступний)
                │
                └── Час НЕ минув → Залишити як є
```

**ВАЖЛИВО:** При вході в гру ми НЕ скасовуємо існуючу нотифікацію, якщо вона ще не спрацювала. Скасування відбувається ТІЛЬКИ коли гравець фактично грає Daily Challenge.

## 15. Верифікація

1. **Компіляція:** Відкрити проект в Unity — модуль має компілюватися без помилок
2. **Інсталяція пакету:** Перевірити що `com.unity.mobile.notifications` з'явився в Package Manager
3. **Конфіг:** Створити `NotificationConfig.asset` в Unity Editor через `Create > Configs > Notification > NotificationConfig`, додати entry для DailyChallenge
4. **Ручне тестування:**
   - **Test 1:** Гравець < level 12 → нотифікація НЕ планується
   - **Test 2:** Гравець досягає level 12 → перша нотифікація планується на 24h
   - **Test 3:** Гравець грає DC → нотифікація переплановується на 24h
   - **Test 4:** Гравець заходить в гру ДО push (14:00 при push 15:00) → push лишається
   - **Test 5:** Гравець заходить в гру ПІСЛЯ push (16:00 при push 15:00) → push планується на завтра
5. **Save data:** Перевірити що файл `notifications_save.json` створюється в `persistentDataPath`
6. **Delivery window:** Протестувати edge cases:
   - Час 09:20 → push на 10:00 (того ж дня)
   - Час 22:15 → push на 10:00 (наступного дня)
   - Час 18:30 → push на 18:30 (без змін)
